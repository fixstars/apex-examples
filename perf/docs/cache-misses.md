# キャッシュミス (Cache Misses)

[← セットアップとインストールは README](../README.md)

`imgpipe` を使った実際の調査手順と出力例です。`imgpipe` の `transform` 関数が行列転置をキャッシュ非効率なストライドアクセスで実行しています。出力の数値は環境によって異なりますが、関数間の比率（`transform` が支配的、`reduce` が次点）は同様になるはずです。

## ステップ 1 — CPU 時間のホットスポットを確認

```
/perf-hotspot
```

インタビューフェーズでは以下を聞かれます:

| 質問 | 答え方 |
|------|--------|
| プロファイル対象がまだありません。どうしますか？ | **実行コマンドを渡す** を選択 |
| プロファイルするバイナリとその引数を教えてください | `./imgpipe --duration 8` |

実際の出力:

```
┌────────┬────────────────────────────────────┐
│ % CPU  │                関数                │
├────────┼────────────────────────────────────┤
│ 56.35% │ transform._omp_fn.0                │
├────────┼────────────────────────────────────┤
│ 35.24% │ reduce._omp_fn.0                   │
└────────┴────────────────────────────────────┘
```

`transform` と `reduce` の 2 関数で CPU 時間の 91% を占めています。

## ステップ 2 — キャッシュミスの粗い帰属

```
/perf-cache
```

インタビューフェーズでは以下を聞かれます:

| 質問 | 答え方 |
|------|--------|
| 作業ディレクトリ ./perf-investigation が既に存在します。どうしますか？ | **そのまま使う / 上書き** |

実際の出力:

```
┌─────────────────────┬──────────┬──────────────┐
│        関数         │ CPU 時間 │ cache-misses │
├─────────────────────┼──────────┼──────────────┤
│ transform._omp_fn.0 │   56.35% │       66.27% │
├─────────────────────┼──────────┼──────────────┤

└─────────────────────┴──────────┴──────────────┘
```

`transform` は CPU 時間・キャッシュミスの両方で上位を占めており、メモリアクセスのボトルネックとして次の調査対象になります。

## ステップ 3 — PEBS による精密な行レベル帰属

```
/perf-cache-miss
```

このスキルは定常状態のライブプロセスへのアタッチが前提です。インタビューフェーズでは以下を聞かれます:

| 質問 | 答え方 |
|------|--------|
| プロファイル対象がまだありません。どうしますか？ | **perf-runner で起動する（推奨）** を選択 |
| 収集パターンを選んでください | **attach — 起動直後からすぐ収集** |
| 各スキルの計測ウィンドウ時間を選んでください | **Smoke (15s / 10s)** |
| 作業ディレクトリ ./perf-investigation が既に存在します。どうしますか？ | **そのまま使う / 上書き** |

perf-runner のインタビュー（スキルが内部で起動）:

| 質問 | 答え方 |
|------|--------|
| 実行するバイナリパスと引数 | `./imgpipe --duration 100`（duration を長くしてアタッチ時間を確保） |
| バイナリのベース名 | `imgpipe` |

実際の出力:

```
=== top_l3_miss ===
41.47  transform._omp_fn.0
 2.10  reduce._omp_fn.0

=== top_source_lines ===
100.00  imgpipe.c:53
```

L3 ミスの **41.47%** が `transform._omp_fn.0` の 1 行（`imgpipe.c:53`）に集中しています。

## ステップ 4 — 命令レベルまでドリルダウン

```
/perf-annotate
```

インタビューフェーズでは以下を聞かれます:

| 質問 | 答え方 |
|------|--------|
| どの `.data` ファイルを使いますか？ | ステップ 3 が収集した `cache-miss-pebs/perf_l3miss.data` |
| ドリルするシンボルを選んでください | `transform._omp_fn.0`（ステップ 3 で 41.47% と表示された関数）|

実際の出力:

```
=== top_instructions ===
 100% :   mov (%rax),%ecx  // imgpipe.c:53

concentrated: true   top_line: imgpipe.c:53   top_line_pct: 100.00
```

単一の `mov` ロード命令に L3 ミスの 100% が集中しています。該当コード:

```c
// imgpipe.c:49-53
static void transform(const uint32_t *src, uint32_t *dst) {
    #pragma omp parallel for schedule(static)
    for (int r = 0; r < dim; r++)
        for (int c = 0; c < dim; c++)
            dst[(size_t)c * dim + r] = src[(size_t)r * dim + c];  // ← imgpipe.c:53
}
```

`dst[c * dim + r]` への書き込みが列ストライドアクセスになっており、毎回キャッシュラインが DRAM から呼び込まれます。

## ステップ 5 — 調査結果をドキュメント化

```
/perf-issue
```

スキルがステップ 1〜4 の収集データとソースコードを読み、`bottleneck-documentation/` 以下に Markdown ファイルを生成します。ファイルには調査のサマリー、原因の説明、修正方向の候補が記載されます。
